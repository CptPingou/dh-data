# P2.1.1 — Mapping DH-DATA → Foundryborne

## Résultat

Cible auditée : **Foundryborne Daggerheart 2.7.2 / Foundry v14**.

La règle est volontairement simple :

> Si Foundryborne possède déjà un type satisfaisant, on l'utilise tel quel.

## Points importants

### Environments

Confirmation : les Environments ne vont **pas** dans les Journals. Foundryborne possède un Actor natif `environment`, avec `tier`, `type`, `impulses`, `difficulty`, `potentialAdversaries`, `notes` et des Feature Items embarqués.

### Campaign Frames

Aucun document Foundryborne spécialisé n'existe. Notre choix précédent reste donc bon :

```text
Campaign Frame
→ 1 JournalEntry
→ plusieurs JournalEntryPage
→ liens @UUID vers contenu mécanique
```

### Domains

Un Domain n'est pas un Item Foundryborne. Les domaines standards vivent dans `CONFIG.DH.DOMAIN`; `allDomains()` fusionne les domaines homebrew provenant des settings avec les domaines du système.

En revanche les cartes sont de vrais Items `domainCard`.

Cela signifie que le futur domaine **Chasse** devra être enregistré comme domaine homebrew/configuration, tandis que ses cartes resteront de vraies Domain Cards.

### Domain Cards Chasse : premier trou concret identifié

La Domain Card native vérifie actuellement, lors de son ajout à un personnage, que le personnage possède une classe donnant accès au domaine de la carte.

C'est important pour notre conception :

```text
Carte Chasse native
        +
progression narrative
```

ne fonctionnera pas totalement sans intervention.

Mais cela ne justifie pas un nouveau système de cartes. La bonne direction est une **petite extension ciblée** du mécanisme d'éligibilité/acquisition lorsque nous arriverons à P2.6.

### Weapons

Les Weapons Foundryborne ont déjà :

- tier ;
- primary/secondary ;
- burden ;
- attack action ;
- weapon features ;
- actions ;
- resource.

C'est une base bien plus riche que nécessaire pour l'import simple, et cela confirme que les futures armes évolutives doivent rester de vraies Weapons avec seulement des données d'évolution supplémentaires.

### Transformations

Foundryborne 2.7.2 ne déclare aucun type `transformation`.

On ne décide rien de plus en P2.1.1.

Elles restent dans DH-DATA jusqu'à ce qu'on teste concrètement si une transformation peut être représentée proprement par :

```text
Journal + Feature Items + ActiveEffects
```

ou si une petite extension est réellement nécessaire.

## Conclusion P2.1.1

Le résultat est favorable : **la très grande majorité de DH-DATA entre directement dans des documents déjà prévus par Foundryborne**.

Les seuls cas non directs identifiés à ce stade sont :

1. `domain` → configuration système ;
2. `campaign_frame` → Journal ;
3. `campaign_mechanic` → Journal-first ;
4. `transformation` → pas de type natif, décision différée ;
5. Domain Cards Chasse → type natif conservé, mais futur petit ajustement d'éligibilité narrative.

Aucun document custom n'est nécessaire pour commencer l'import.
