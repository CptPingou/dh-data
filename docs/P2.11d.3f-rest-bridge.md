# P2.11d.3f — Bridge repos long natif Foundryborne 2.10.6

## Observation de la sonde 3f.0

- Après annulation : aucun événement capturé.
- Après validation du repos long : un `createChatMessage` de type `base`, avec
  `system.actor: Actor.<id>`, `system.moves[].movePath` préfixés
  `longRest.moves.`, et `content` contenant `daggerheart chat downtime`.
- Aucun `updateActor` n'a été capturé pendant cette procédure.

Le bridge **ne** réagit **pas** à un `createChatMessage` quelconque, un repos court,
une dépense de mouvement de repos ou un changement de PV/Stress. Il vérifie
également `speaker.actor == system.actor` et que l'Actor est permanent.

## Cycle de vie

- La suppression est ciblée par **porteur**, indépendamment du fabricant.
- L'ID de la carte de repos est conservé dans le setting mondial
  `processedRestMessageIds` : traiter deux fois cette même carte est idempotent,
  même si elle n'a expiré aucune infusion.
- Seul le compte MJ actif élu parmi les clients MJ installe un traitement
  effectif (les autres ignorent l'événement) ; la file sérialise les écritures.
- Aucun Actor Artificier n'est nécessaire.
- Pas de réimport de compendium ni de migration du setting.

## Limite

Ce raccordement est fondé sur **la carte effectivement émise** dans la sonde
Foundryborne 2.10.6. Si un autre workflow natif de repos n'émet pas cette carte,
le bridge n'expirera pas silencieusement les infusions. À valider en jeu.

## Test runtime (ne pas utiliser sur des infusions importantes)

1. Après déploiement, créer une infusion temporaire sur un porteur test.
2. Ouvrir et annuler son repos long : l'infusion doit rester.
3. Ouvrir et **valider** son repos long natif : la console doit afficher
   `native long rest -> world infusions`, avec `expiredCount: 1`.
4. `inf.status().entries.filter(e => e.targetActorUuid === porteur.uuid)`
   doit être vide. Les infusions d'autres personnages doivent rester.
5. F5 : le résultat reste vide.
