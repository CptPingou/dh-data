# Monster Hunter Daggerheart --- Cadrage UI, logistique, recherche et progression

## 1. Objectif

La réforme de l'interface Expédition doit soutenir une boucle de jeu
inspirée des extraction shooters, adaptée à Monster Hunter / Daggerheart
:

**chasser → collecter → choisir ce qui est ramené → sécuriser au FOB →
sélectionner ce qui mérite l'extraction stratégique → transporter par
caravane → exploiter à la base → progresser → repartir.**

Les contraintes de slots, les installations du FOB, l'état de la
Caravane, la Recherche, les voies Artisan / Artificier et les déblocages
par récompense deviennent des éléments de gameplay.

Principe architectural : les règles restent dans les données, policies,
capabilities et projections. Les vues Foundry et Web ne portent pas les
règles métier.

## 2. Structure cible de l'interface

Interface joueur :

-   **Expédition** : tableau de bord de l'arc.
-   **Inventaire** : sacs et stockages accessibles.
-   **FOB** : camp temporaire, installations et activités.
-   **Caravane** : véhicule durable, composants, traction et chargement.
-   **Atelier** : craft, infusions et modifications des armes de chasse.
-   **Recherche** : graphe des connaissances découvertes.
-   **⚙ MJ** : administration logistique, FOB, Caravane et progression.

FOB et Caravane sont des objets métier à part entière, pas seulement des
onglets de stockage.

## 3. Boucle d'extraction

``` text
BASE
  ↓ préparation
EXPÉDITION / CHASSE
  ↓ collecte
SACS DES CHASSEURS
  ↓ extraction terrain
FOB
  ↓ extraction de fin d’arc
CARAVANE
  ↓ retour
BASE / ATELIER AVANCÉ
```

### Sac

Première contrainte d'extraction. Les joueurs choisissent ce qu'ils
rapportent en fonction des slots disponibles.

### Sol

Zone d'échange immédiat : `Sac A → Sol → Sac B`. Ce n'est pas un
stockage durable.

### FOB

Stock temporaire de l'arc. Seul ce qui est effectivement ramené dans les
sacs rejoint le FOB.

### Caravane

Second palier d'extraction. En fin d'arc, le groupe choisit ce qui
quitte le FOB en fonction des slots disponibles dans les caravanes. Ce
qui n'est pas extrait doit être abandonné, consommé ou transformé selon
les futures règles.

## 4. Modèle logistique générique

Le moteur ne doit pas supposer `1 entrée = 1 slot`.

### Objets

Les définitions d'items doivent pouvoir porter :

``` json
{
  "storage": {
    "slots": 1,
    "stackable": true,
    "stackLimit": 10,
    "allowedContainers": ["backpack", "ground", "fob", "caravan", "base"]
  }
}
```

Besoins : - slots occupés ; - stackable ; - stackLimit ; - compatibilité
éventuelle avec les types de contenant.

Ces propriétés restent data-driven.

### Contenants

Ils exposent au minimum : - capacité en slots ; - rôle ; - règles
d'accès ; - règles de stockage ; - limites de stack éventuelles ; -
lifecycle si nécessaire.

`transfer(quantity)` reste la primitive bas niveau pour split, merge et
déplacement.

## 5. Capabilities directionnelles

`receive / transfer` par contenant est trop grossier. L'autorisation
doit pouvoir dépendre du viewer, de la source, de la destination, de la
phase et des règles du contenant.

Phases envisagées :

``` text
field             : Sac ↔ Sol
field-extraction  : Sac → FOB
arc-logistics     : gestion du FOB selon les règles de l’arc
arc-extraction    : FOB → Caravane
returned          : Caravane → Base
```

La primitive de transfert exécute une action déjà autorisée ; elle ne
décide pas de la règle métier.

## 6. Page FOB

Le FOB est un camp temporaire et modulaire avec : 1. capacité de
stockage ; 2. emplacements d'installations.

Installations possibles : - cuisine ; - atelier de brousse ; - poste
d'analyse/recherche ; - forge légère ; - futures installations
spécialisées.

Une installation doit être data-driven :

``` json
{
  "id": "mh.facility.field-kitchen",
  "kind": "facility",
  "tier": 1,
  "slotCost": 1,
  "unlocks": ["rest.activity.cooking"]
}
```

La page montre installations, emplacements libres, état, stockage et
activités de repos disponibles.

Disponibilité d'une activité :

``` text
connaissance
+ recette débloquée
+ installation requise
+ type de repos
+ ressources
= activité disponible
```

## 7. Page Caravane

La Caravane est un véhicule/logistique persistant avec : - capacité de
chargement ; - composants ; - état des composants ; - traction ; -
équipements ; - maintenance.

Composants : châssis, roues, attelage, etc.

Exemple :

``` json
{
  "components": [
    {
      "slot": "chassis",
      "definitionId": "mh.caravan.chassis.standard",
      "condition": 8,
      "maxCondition": 10
    }
  ]
}
```

Les animaux de traction restent séparés des composants mécaniques afin
de pouvoir avoir leurs propres états, fatigue, propriétés et capacités.

Le panneau MJ édite l'état ; les pages FOB et Caravane le représentent

## 9. Recherche : Knowledge Graph

Recherche devient un graphe de connaissances :

``` text
MATÉRIAU
   ↓
PROPRIÉTÉ
   ↓
APPLICATION
   ├── craft
   ├── infusion
   └── modification d’arme de chasse
```

Exemple :

``` text
Glande de Tetsucabra
        ↓
    PARALYSIS
      /     \
     ↓       ↓
Infusion   Modification
Artificier   Artisan
```

Types initiaux de nodes : - `MATERIAL` - `PROPERTY` - `APPLICATION`

Les relations sont elles-mêmes découvrables. Un joueur peut connaître un
matériau, puis une propriété, puis seulement plus tard une application.

Les éléments inconnus ne doivent jamais être transmis avec leur
véritable identité au client joueur ou au Web.

## 10. Progression et récompenses

Infusions et recettes d'armes de chasse peuvent être distribuées comme
récompenses.

États :

``` text
caché
  ↓
existence révélée
  ↓
compris
  ↓
craft débloqué
  ↓
disponible lorsque les conditions sont réunies
```

Le panneau MJ doit permettre : - révéler l'existence ; - définir/révéler
le bénéfice ; - définir/révéler les ressources ; - débloquer le craft
; - proposer lors d'un repos ; - envoyer manuellement au chat.

Classement et filtres par Tier, type et état. Le Tier appartient aux
données.

## 11. Repos

Le rail de repos existant doit déterminer les opportunités à partir de
: - connaissances ; - recettes débloquées ; - ressources ; -
installation requise ; - type de repos ; - contexte.

Les opportunités pertinentes peuvent être envoyées dans le chat. Une
déduplication doit éviter le spam à chaque repos.

## 12. Artisan / Artificier et armes de chasse

`Motherboard` reste l'identifiant technique ; l'interface joueur dit
**arme de chasse**.

Le budget final reste inchangé mais se répartit entre deux voies :

-   **Artisan** : modifications durables, structure, mécanismes,
    renforts.
-   **Artificier** : infusions temporaires, renouvelées selon leurs
    règles.

``` text
ARME DE CHASSE
      │
budget total inchangé
      │
 ┌────┴────┐
 ↓         ↓
ARTISAN  ARTIFICIER
durable  temporaire
 └────┬────┘
      ↓
potentiel complet
```

Exemple :

``` json
{
  "motherboard": {
    "capacity": 6,
    "allocation": {
      "modification": 3,
      "infusion": 3
    }
  }
}
```

La répartition peut être data-driven (`3/3`, `4/2`, `2/4`...), sans
augmenter le budget total.

Découvrir une propriété ne révèle pas automatiquement ses deux
applications Artisan et Artificier.

## 13. Export Web intersession

Le Web est d'abord une projection en lecture seule de l'état Foundry
validé :

``` text
FOUNDRY
  source autoritaire
      ↓
validation fin de session
      ↓
snapshot player-safe
      ↓
CampaignRepo / NAS
      ↓
WEB READ ONLY
```

Le Web présente : - Expédition ; - Inventaires ; - FOB ; - Caravane ; -
Atelier ; - Recherche ; - progression révélée.

Le site ne refait pas la sécurité : le snapshot doit déjà être
player-safe.

`expedition-web-snapshot.mjs` reste la frontière de sécurité.

## 16. Invariants

1.  Foundry reste autoritaire pendant la session.
2.  Le Web V1 reste en lecture seule.
3.  Une information secrète n'est jamais simplement masquée par l'UI :
    elle n'est pas projetée.
4.  Les règles métier ne résident pas dans les vues.
5.  Le homebrew doit rester principalement data-driven.
6.  `Motherboard` reste technique ; **arme de chasse** est le
    vocabulaire joueur.
7.  La séparation Artisan / Artificier n'augmente pas le budget total de
    l'arme.
8.  FOB et Caravane sont des objets de gameplay distincts.
9.  Les slots sont la pression logistique principale, sans simulation de
    poids.
10. Recherche représente une progression de connaissance, pas un simple
    catalogue.
